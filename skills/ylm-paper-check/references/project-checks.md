# LaTeX 工程检查方法

使用已有项目工具，不依赖旧版扫描脚本。搜索结果是候选证据，LaTeX 命令可以被宏、条件和环境改变，不能把正则匹配当作完整 TeX 解析。

## 目标与基线

- 从用户指定主文件、构建说明、Makefile、`.latexmkrc`、编辑器设置和 `% !TeX program` 等已有信息确定目标。检查配置内容再执行其中的构建动作。
- 跟随主文件实际使用的 `\input`、`\include`、导入命令、宏包和参考文献声明，记录缺失或无法静态解析的依赖。不要把目录中的旧稿、模板例子和未包含章节一起计入全文。
- 使用 `git status` 和相关 `git diff`（有版本库时），并保存将要编辑的源文件基线。无版本库时使用隔离目录的源文件副本；不得重置或 stash 用户修改。
- 对不能展开的动态包含或条件分支，使用构建日志／记录文件和人工阅读补充，明确剩余覆盖限制。

## 编译

优先采用明确的项目构建命令及既有配置。没有命令但引擎有充分证据时，使用相符的 `latexmk` 模式，例如 pdfLaTeX 的 `-pdf`、XeLaTeX 的 `-xelatex` 或 LuaLaTeX 的 `-lualatex`；普通 `article` 工程无其他引擎要求时可选 pdfLaTeX，并说明依据。引擎仍不确定时不要用失败的猜测编译判稿件错误。

在原工程的工作目录或保留依赖布局的隔离副本内构建，不能只复制主文件而丢失图片、类文件等。构建生成的辅助文件与论文源文件分别处理。不要清理用户已有产物，也不因审查自行启用 shell escape。

- 每个目标版本由一个明确的任务所有者编译。集成任务中协调者默认负责；只有显式委派时由检查模块负责，其他角色不重复运行。
- 同一任务通常一次基线编译、一次修订后编译；只在更改、失败或未解决问题要求时增加。审查不产生修订版本时无需重复编译。
- 保存退出状态和日志，辨别未定义引用、缺字、缺字体／宏包、排版警告及源码错误。`latexmk` 可用也不代表本项目依赖齐全。
- 编译超时先报告未完成及已知日志，不据此宣称源码损坏。使用有界等待，并在长构建期间保持必要进度沟通。

## 阅读和搜索检查

用 `rg` 或已安装的项目工具定位定义与用法，然后结合源文件和日志复核：

- 标签是否重复，引用是否对应实际目标，前向引用是否已在完整构建后解析。不能把仅首次编译的未解析状态直接当最终错误。
- 引用键是否存在于所声明数据库，宏生成的引用是否漏检，作者／年份式和数字式格式是否遵守项目约定。没有 `.bib` 时也检查手写 `thebibliography`、提供的 `.bbl` 和工程实际采用的来源。
- 未使用的 BibTeX 条目通常只是库中备用资料，不直接当阻断问题。
- 术语和缩写、同一数学对象的符号、算法名及环境名称是否一致；含义不同的相似名词不要统一。
- 图表与公式的文字、单位、数值和正文叙述是否一致；使用的统计量是平均、最大还是最终值，比较预算是否相同。
- 摘要、方法、结果和结论是否对相同主张使用了相同条件与强度；超时、未证最优和启发式身份需准确区分。

范围内只有文本或片段时，不运行工程构建，不推断缺失的标签／引用一定不存在，明确无法检查全文的部分。

## 修复后的检查

对已批准的结构修复检查定义与所有相关用法；不能只改一个调用点而制造新矛盾。比较源文件差异，核对未授权区域未被修改；使用同一目标及可比较的构建方式检查前后状态。非阻断的排版警告与科学语义风险分别报告。
